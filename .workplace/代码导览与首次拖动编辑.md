# 3DGS-Drag 代码导览与 Windows 首次拖动编辑

这份文档回答两个问题：论文中的 pipeline 在代码里对应什么，以及如何在当前这台 Windows 电脑上完成第一次拖动编辑。

> 当前检查结果（2026-09-21）：电脑有 RTX 5060 Laptop GPU（约 8 GB 显存）；`rag` 环境已有 Python 3.11.14 和 PyTorch 2.10.0+cu128，GPU 可用。两个项目子模块的源码已经完整。当前新增的是 Visual Studio Build Tools 2026（MSVC 19.51）及 Windows 11 SDK，并非 CUDA 12.8 官方支持的 Visual Studio 2022/MSVC 19.3x；CUDA Toolkit、独立 `draggs` 环境和项目 CUDA 扩展尚未安装。仓库中也没有示例数据或训练好的 Gaussian `.ply`，因此尚不能标记为“本机已完整跑通”。

## 1. 先把论文 pipeline 对应到代码

当前代码的实际执行顺序是：

```text
COLMAP/NeRF 数据集 + 训练好的 3D Gaussian PLY + 拖动 JSON
                         │
                         ▼
加载场景、相机和 Gaussian；用控制点附近的多个 Gaussian 建立拖动区域
                         │
                         ▼
渲染原始场景的多视角图像，并用这些图像训练一次 DreamBooth LoRA
                         │
                         ▼
对每个拖动步骤：复制所选 Gaussian → 计算形变 → 降低旧 Gaussian 的不透明度
                         │
                         ▼
渲染形变后的多视角图像 → LoRA 扩散模型做 img2img，生成二维监督图像
                         │
                         ▼
用可微 Gaussian 渲染和图像损失优化 3D Gaussian
                         │
                         ▼
按退火强度重复“扩散编辑 → Gaussian 优化”，再进入下一拖动步骤
```

你的原 pipeline 基本正确，但要修正两点：

1. LoRA 微调发生在拖动循环之前，只训练一次，不是在每次形变后重新训练。
2. 扩散模型不直接修改 Gaussian 参数。它先生成多视角二维目标图，随后可微渲染产生的损失再反向更新 Gaussian。

主调用链如下：

```text
train_drag.py: main
  └─ training
      ├─ init_scene_and_gaussians
      │   ├─ Scene(...)                         读取数据集和相机
      │   ├─ gaussians.load_ply(...)            读取预训练 3DGS
      │   ├─ Drag(...)                          读取控制点并选择 Gaussian
      │   ├─ render_sets_train(...)             渲染原始多视角图
      │   └─ DreamBooth.train_dreambooth(...)   训练一次 LoRA
      └─ run_drag_training_loop
          ├─ apply_one_drag_step
          │   └─ drag_copy_paste_step_deform
          ├─ run_one_edit_pass
          │   └─ DreamBooth.img2img             生成二维编辑目标
          └─ optimize_gaussians_for_edits       用图像损失优化 Gaussian
```

### “一个控制点”在代码里究竟是什么

JSON 中的一个 `start: [x, y, z]` 是三维坐标，不是某个 Gaussian 的编号。代码会选取距离该坐标小于 `voxel_size` 的一簇 Gaussian，并把它们标成同一个拖动区域。随后，代码还会用这簇 Gaussian 的平均位置重新定位控制点。

所以：

- JSON 可以包含一个或多个稀疏控制点；
- 每个控制点在内部控制的是附近的一簇 Gaussian；
- `direction[i]` 是第 `i` 个控制点的总位移，目标点为 `start[i] + direction[i]`；
- `drag_steps` 会把总位移均分成多步；
- `cluster` 可把多个控制点分组，每组共同控制一部分 Gaussian；
- `mode: "move"` 会把旧位置 Gaussian 的不透明度降到约 `0.01`；`mode: "extend"` 则保留到约 `0.5`；
- 示例 JSON 里的 `local_mask` 当前没有被 `train_drag.py` 使用。

这里所谓 copy-paste 的代码含义是：复制被选中的 Gaussian 属性，把副本形变到新位置，再降低旧位置 Gaussian 的不透明度。真正执行的位置是 `scene/gaussian_model_drag.py` 的 `deform_points()`。

## 4. 在这台 Windows 电脑上准备环境

### 4.1 为什么不能照抄 README 的 CUDA 11.8

这台电脑的 RTX 5060 属于 Blackwell。PyTorch 从 2.7 开始提供 Blackwell 支持，并提供 CUDA 12.8 wheel；官方的 Windows 安装表也给出了 PyTorch 2.7.1 + CUDA 12.8 的组合。因此本机建议从这个组合开始，而不是 README 的 CUDA 11.8。

截至 2026-09-22，NVIDIA 最新正式版是 CUDA Toolkit 13.4.2，CUDA 13.4 已支持 Visual Studio 2026/MSVC 19.5x。但本项目不应仅因版本更新就改用 13.4：计划安装的 PyTorch 是 `cu128`，即它本身使用 CUDA 12.8 构建；PyTorch 在编译本地扩展时会检查 Toolkit 版本，跨越 CUDA 12 与 13 的主版本容易直接报错。若改成 CUDA 13.4，还要同时更换支持 CUDA 13 的 PyTorch、扩散模型和 `bitsandbytes` 组合，给旧研究代码增加新的兼容变量。首次复现优先保持 PyTorch、Toolkit 和 CUDA 扩展都在 12.8，再单独实验升级。

参考资料：

- [PyTorch 2.7 的 Blackwell 与 CUDA 12.8 支持](https://pytorch.org/blog/pytorch-2-7/)
- [PyTorch 2.7.1 官方安装命令](https://pytorch.org/get-started/previous-versions/#v271)
- [CUDA 12.8 Windows 安装指南](https://docs.nvidia.com/cuda/archive/12.8.1/cuda-installation-guide-microsoft-windows/index.html)
- [NVIDIA CUDA Toolkit 版本归档与最新版](https://developer.nvidia.com/cuda-toolkit-archive)
- [CUDA 13.4 Windows 编译器支持表](https://docs.nvidia.com/cuda/cuda-installation-guide-microsoft-windows/)
- [bitsandbytes 的 Windows/CUDA 12.8 支持表](https://huggingface.co/docs/bitsandbytes/v0.46.0/installation#cuda)

### 4.2 安装编译工具

CUDA 扩展需要本地 C++ 编译器。Visual Studio Build Tools 2022 17.14.41 已安装，并额外安装了 v14.39 工具集；使用 `vcvarsall.bat x64 -vcvars_ver=14.39` 后，已经确认实际调用的是 x64 MSVC 19.39.33523，满足 CUDA 12.8 所需的 MSVC 19.3x 组合。原有 Visual Studio Build Tools 2026/MSVC 19.51 可以继续保留，但不能用于本项目的 CUDA 12.8 扩展编译。

当前只剩 CUDA Toolkit 这一个系统安装任务：

CUDA Toolkit 12.8 已安装到 `D:\NVIDIA\CUDA\v12.8`，并已验证 `nvcc` 为 12.8.93。系统编译链已经完整。

Visual Studio 2022 与 2026 可以并存，不需要卸载已经安装的 2026。安装完成后必须打开 **Developer PowerShell for VS 2022**，不能打开 2026 版本。

验证时同时检查工具路径和版本：

```powershell
where.exe cl
cl

where.exe nvcc
nvcc --version

nvidia-smi
```

合格状态是：当前 shell 使用 MSVC 19.3x，而不是已检测到的 19.51；`nvcc` 显示 release 12.8。安装多个 MSVC 工具集后，路径未必直观，因此以 `cl` 输出的版本为最终判断。仅有 `nvidia-smi` 说明显卡驱动存在，不代表能够编译 CUDA 扩展。

### 4.3 建立 Python 环境

现有 `rag` 环境已经证明 PyTorch 可以驱动 RTX 5060，但不建议直接把研究代码依赖装进去：它使用 Python 3.11、PyTorch 2.10，并承担其他 RAG 工作，修改 `diffusers`、`transformers`、`peft` 等包可能破坏原环境。为 3DGS-Drag 单独建立 Python 3.10 环境更容易定位兼容性问题。

每次重新打开 **x64 Native Tools Command Prompt for VS 2022** 后，先恢复本项目使用的编译器和 CUDA 路径：

```bat
call "D:\Program Files (x86)\Microsoft Visual Studio\2022\BuildTools\VC\Auxiliary\Build\vcvarsall.bat" x64 -vcvars_ver=14.39
set CUDA_HOME=D:\NVIDIA\CUDA\v12.8
set PATH=%CUDA_HOME%\bin;%PATH%
```

然后建立环境。这里使用 conda-forge 并覆盖默认 channels，避免 Anaconda Terms of Service 尚未接受时创建失败：

```bat
cd D:\papers\3DGSdrag\code\3DGS-Drag
conda create -n draggs -c conda-forge --override-channels python=3.10 -y
conda activate draggs
where python
python --version
```

只有在 `where.exe python` 的第一项指向 `D:\Miniconda3\envs\draggs\python.exe`，且版本显示 Python 3.10 后，才继续安装。不要在 `conda create` 或 `conda activate` 报错后继续执行 `pip`，否则依赖会落进 base 环境。使用 `--override-channels -c conda-forge` 可以避开默认 Anaconda channels 尚未接受 Terms of Service 导致的创建失败。

如果不希望约 3.3 GB 的 PyTorch 下载缓存占用 C 盘，可以把本次终端的 pip 缓存和临时目录放到 D 盘：

```bat
if not exist D:\pip-cache mkdir D:\pip-cache
if not exist D:\pip-temp mkdir D:\pip-temp
set PIP_CACHE_DIR=D:\pip-cache
set TEMP=D:\pip-temp
set TMP=D:\pip-temp
```

确认环境无误后再安装：

```bat
python -m pip install --upgrade pip setuptools wheel
python -m pip install torch==2.7.1 torchvision==0.22.1 --index-url https://download.pytorch.org/whl/cu128
python -m pip install -r requirements.txt
python -m pip install psutil requests ninja
```

`requirements.txt` 没有锁版本，而且漏列了主流程直接导入的 `psutil` 和 `requests`。`ninja` 可以加快 CUDA 扩展构建，但不是 GPU 运行时。`scipy` 只被主流程不调用的 `utils/knn.py` 使用，第一次复现不用安装。`pybind11` 的必要头文件由 PyTorch 扩展工具提供，这两个子模块也不使用 Cython。如果扩散模型库的最新版出现 API 不兼容，应先记录错误和版本，再做有依据的版本固定；不要一次随意降级多个包。

验证 PyTorch 是否真正识别 RTX 5060：

```powershell
python -c "import torch; print(torch.__version__); print(torch.version.cuda); print(torch.cuda.is_available()); print(torch.cuda.get_device_name(0))"
```

本机已验证：PyTorch `2.7.1+cu128`、CUDA runtime `12.8`、`torch.cuda.is_available() = True`，设备为 `NVIDIA GeForce RTX 5060 Laptop GPU`，计算能力为 `(12, 0)`。

### 4.4 编译 CUDA 扩展

`diff-gaussian-rasterization`、它依赖的 GLM 和 `simple-knn` 源码均已完整，子模块初始化任务已经完成，不需要再次运行 Git 命令。安装好 CUDA 12.8 并激活 `draggs` 环境后直接编译：

```bat
set CUDA_HOME=D:\NVIDIA\CUDA\v12.8
set PATH=%CUDA_HOME%\bin;%PATH%
set DISTUTILS_USE_SDK=1
set MSSdk=1
set TORCH_CUDA_ARCH_LIST=12.0

python -m pip install --no-build-isolation -v .\submodules\diff-gaussian-rasterization
python -m pip install --no-build-isolation -v .\submodules\simple-knn
```

PyTorch 2.7.1 在已激活的 Visual Studio Developer Command Prompt 中构建扩展时，要求 `DISTUTILS_USE_SDK=1`，否则会在真正调用编译器前终止，以避免 setuptools 再次初始化 Visual C++ 环境。`MSSdk=1` 明确告诉 distutils 直接使用当前已配置的 Windows SDK。

验证：

```powershell
python -c "import diff_gaussian_rasterization; import simple_knn; print('CUDA extensions OK')"
python train_drag.py -h
```

### 4.5 这些依赖分别做什么

可以把依赖理解成五层。上一层会调用下一层，所以“PyTorch 已经能用 GPU”并不等于“已经能编译项目的 CUDA 算子”。

```text
3DGS-Drag Python 主程序
  ├─ 扩散模型与 LoRA：diffusers / transformers / peft / accelerate / bitsandbytes
  ├─ 3DGS CUDA 扩展：diff-gaussian-rasterization / simple-knn
  ├─ 深度学习运行时：PyTorch + torchvision
  └─ 系统编译链：MSVC + Windows SDK + CUDA Toolkit/nvcc + NVIDIA 驱动
```

#### 系统与编译层

| 依赖 | 作用 | 当前状态 |
|---|---|---|
| NVIDIA 驱动 | 让 Windows 和 CUDA 程序访问 RTX 5060；决定可运行的最高 CUDA 版本 | 已有 576.88，可运行 CUDA 12.8 |
| VS 2022 MSVC | 编译扩展中的 C++ 文件，并与 CUDA 目标文件链接成 Python 可加载的 `.pyd` | 已安装并验证：v14.39 / MSVC 19.39.33523 / x64 |
| Windows SDK | 提供 Windows 头文件、库和链接工具 | 已随 Build Tools 2026 安装，可复用 |
| CUDA Toolkit 12.8 | 提供 `nvcc`、CUDA 头文件和开发库，用来把 `.cu` 源码编译为 RTX 5060 可执行代码 | 已安装到 `D:\NVIDIA\CUDA\v12.8`；已验证 nvcc 12.8.93 |
| CMake | 通用 C/C++ 构建系统 | 已安装，但这两个扩展的 `setup.py` 不直接使用它 |
| Git 与子模块 | 获取 rasterizer 和 GLM 的固定源码版本 | 已完成，可跳过 |

显卡驱动、PyTorch wheel 和 CUDA Toolkit 是三件不同的东西：驱动负责执行；PyTorch wheel 自带运行库，让预编译的 PyTorch 算子运行；Toolkit 提供 `nvcc`，负责把本项目的新 CUDA 源码编译出来。

#### Python 与 PyTorch 层

| 依赖 | 作用 | 是否必要 |
|---|---|---|
| conda + Python 3.10 | 给论文代码建立隔离环境，避免改坏现有 `rag` 环境 | 必要；Python 3.10 会随环境自动安装 |
| PyTorch 2.7.1+cu128 | Tensor、自动求导、GPU 执行，同时为 CUDA 扩展提供构建接口和 C++ 头文件 | 已安装并验证，可识别 RTX 5060 / sm_120 |
| torchvision 0.22.1 | 图像变换与保存，并提供感知损失使用的 VGG16 | 必要 |
| setuptools / wheel | 把两个 C++/CUDA 扩展构建、打包并安装进环境 | 必要 |
| ninja | 并行执行扩展编译，主要作用是加快构建 | 推荐，但不是算法依赖 |

#### 3DGS 专用 CUDA 扩展

| 依赖 | 作用 | 对应 pipeline |
|---|---|---|
| `diff-gaussian-rasterization` | 把 3D Gaussian 投影并混合成二维图像，同时支持反向传播 | 所有多视角渲染、mask 渲染和用图像损失优化 Gaussian |
| `simple-knn` | 在 GPU 上计算点之间的近邻距离，主要用于初始化 Gaussian 的尺度 | 从 COLMAP 点云建立初始 3DGS；加载和训练基础模型时需要 |

`diff-gaussian-rasterization` 不是 3DGS-Drag 作者重新编写的模块。仓库通过 `.gitmodules` 引用了原始 3D Gaussian Splatting 团队 Inria GraphDeco 的公开仓库 `https://github.com/graphdeco-inria/diff-gaussian-rasterization`，并固定在提交 `9c5c2028f6fbee2be239bc4c9421ff894fe4fbe0`（`toggle antialiasing`）。3DGS-Drag 的渲染调用依赖这个版本提供的抗锯齿参数和返回值接口，因此不要随意把子模块替换成其他提交。

这两个包没有适用于当前仓库固定版本和显卡架构的现成 wheel，所以必须在本机用 MSVC 和 `nvcc` 编译。

#### 扩散模型与 LoRA

| 依赖 | 作用 | 对应 pipeline |
|---|---|---|
| `diffusers` | 加载 Stable Diffusion 1.4，并对形变后的渲染图执行 img2img | 生成二维编辑监督图 |
| `transformers` | 使用 BLIP 给原始场景自动生成文字描述，并提供 Stable Diffusion 文本编码器 | LoRA 提示词和文本条件 |
| `peft` | 给 UNet 和文本编码器插入、保存和加载 LoRA 低秩适配器 | 场景专用 LoRA |
| `accelerate` | 启动并管理 LoRA 混合精度训练 | `accelerate launch utils/train_dreambooth_lora.py` |
| `datasets` | LoRA 训练脚本使用的 Hugging Face 数据与日志工具 | DreamBooth LoRA 训练 |
| `bitsandbytes` | 提供 8-bit Adam，降低 LoRA 优化器显存；代码固定传入 `--use_8bit_adam` | 8 GB 显存机器上的 LoRA 训练 |

| 依赖 | 作用 | 是否必要 |

## 8. 这台 8 GB 显存电脑最可能遇到的问题

### CUDA out of memory

先保留 `-r 2`，把 `--camera_num` 降到 4 或 8，并关闭其他占用 GPU 的程序。不过当前代码在 LoRA 之前仍会一次性堆叠并缩放全部相机渲染图，降低 `camera_num` 不能降低这一段的峰值；若这里 OOM，需要修改代码为分批保存原始渲染，而不是继续盲目降低 `camera_num`。

LoRA 同时训练 UNet 和文本编码器，8 GB 也可能不足。若发生在 `train_dreambooth_lora.py`，下一步应给 LoRA 命令加入 gradient checkpointing 或改用显存更大的服务器。这属于兼容性调整，完成首次原样运行前不要把它与论文方法改动混在一起。

### `cl` 或 `nvcc` 找不到

这不是 Python 包问题。确认你使用的是 Developer PowerShell for VS 2022，并且 CUDA 12.8 Toolkit 已安装；然后重新设置 `CUDA_HOME`。

### `No module named diff_gaussian_rasterization` 或 `simple_knn`

子模块没有拉取，或 CUDA 扩展没有在当前 `draggs` 环境编译成功。重新检查第 4.4 节，不要只执行 `pip install -r requirements.txt`。

### `Could not recognize scene type!`

`-s` 指错了目录。它必须直接指向包含 `sparse/` 的 COLMAP 场景根目录，或包含 `transforms_train.json` 的 Blender/NeRF Synthetic 根目录。

### 控制点选不到 Gaussian，出现空集合或 NaN

配置与场景坐标系不匹配，或 `voxel_size` 太小。官方配置只能直接用于对应官方示例；自定义数据必须重新选点。

### Hugging Face 下载或授权失败

确认能访问 Hugging Face，已经接受 Stable Diffusion 1.4 的模型条款，并执行 `hf auth login`。默认缓存位于 `C:\Users\Legiony\.cache\huggingface`；本机已规划使用 `HF_HOME=D:\huggingface-cache`。模型、Xet 临时分块、LoRA 缓存和重复副本会占用较多磁盘空间，运行前应预留 12–20 GB。

## 9. 阅读代码时值得记录的实现差异

当前代码是复现研究代码，不能默认每一行都与论文公式逐字一致。尤其注意：

- 相机先按拖动区域可见面积排序，随后代码又对整个排序结果做随机打乱，因此实际选择的并不是严格的“可见面积前 50 个视角”。
- `scene/deform.py` 的距离权重实现与论文第 3.3 节公式需要逐项对照，尤其是保留最近两个控制点后的权重符号和归一化。
- `run_one_edit_pass()` 调用 img2img 时没有传入 mask；mask 主要在后续 Gaussian 优化的背景保持损失中使用。
- 主循环中没有调用 `Drag.drag_loss()`、`track_point()` 或 `track_point_idx()`。
- 扩散模型返回的 `weight` 会写入相机对象，但当前优化损失没有使用该权重。

第一次复现应先保持代码不变并保存结果。跑通后，再把这些差异逐个做成消融或修复实验，这样才能区分“论文方法效果”“官方实现行为”和“你的改动效果”。
